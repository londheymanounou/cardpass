# What CardPass can (and must not) take from the Bio-Resonant core

Written for whoever works in this folder. **Applied (2026-10-07): section 3**, the spring easing and the 80 / 161 / 321 ms tiers,
generated by `tools/gen_br_motion.py` into `components/ui/motion_br.h` (selection 80 ms, slides and toasts 161 ms). Sections 1, 2
and 4 needed no change (no frame buffer, strip hashes wiped, text size left for the device). The source of truth is `D:\bio-resonant-ui`
(`core/`, `platforms/`, `src/engine`). CardPass already ships its own Bio-Resonant UI (PROGRESS.md "Bio-Resonant UI"), so
this note is short: one thing worth taking, two warnings, and one design question.

## 1. Do NOT adopt the core's rasteriser — it breaks two of this project's rules
`core/br_raster.h` draws into a **full 240x135 RGB565 frame buffer (63 KB)**. PROGRESS.md already records why that is out: "a 65 KB
full-frame sprite left [deck] ~1 KB from a boot failure", and static RAM here is 68 KB already. The core's strip-free design
is right for the browser preview and a roomier device; it is wrong for CardPass. Keep the strip renderer.

The core's *contract* (a screen emits a draw list, a backend executes it) is compatible with strips: a CardPass backend would
execute the same list once per 16-row band instead of into a frame buffer. That is a rewrite of every screen's drawing calls,
so it is only worth it if you want the browser preview or the shared cross-platform tests. Not recommended now.

## 2. Security: the core's draw list is not safe for secrets as written
If any CardPass screen ever goes through the core's `BrList` (`core/br_core.h`):
- `br_emit_text` **copies the string into a static 512-byte pool** that is never wiped. A revealed password, a TOTP code or a
  decrypted field would sit there until overwritten. It violates "fixed buffers, wiped with `mbedtls_platform_zeroize()` right
  after use". Any adoption must zeroize the pool as soon as the backend has consumed the list, and mask by default.
- The core's frame buffer keeps the rendered pixels of whatever was shown. (The strip hashes here are already wiped on close
  for the same reason: they fingerprint the screen. Keep that rule for anything new.)
- The browser preview (`src/cardputer-preview.html`) and the golden-hash tests run in a normal browser/PC process whose memory is
  never wiped. **Use fake data only; never load a real database or password into it.** (Same spirit as "never test with a real
  database until the stage's tests pass".)

## 3. One thing worth taking: the token easing, instead of ease-out quad (small, and it fits the strip design)
`components/ui/app_anim.c` eases with `256 - (r*r>>8)` (ease-out quad) and hard-coded durations: `SEL_MS 100`, `SLIDE_MS 130`,
`TOAST_MS 120`. The design system defines motion as a **spring** (omega 24.39 rad/s, zeta 0.82) and three tiers: feedback 80 ms,
element **161 ms**, view 321 ms. The tokens ship the spring's step response as a 25-point table (`motion.easing`).

That is exactly a "pure function of state + time", so it needs no framebuffer and no per-frame state: swap the quad for a table
lookup with linear interpolation. Values in Q8 (0..256), generated from `dist/tokens.json`:

```c
/* motion.easing: the element-tier spring step response sampled at 25 evenly spaced times (0 .. duration) */
static const uint16_t BR_EASE[25] = { 0, 3, 11, 23, 38, 54, 72, 89, 106, 123, 139, 154, 167, 180, 191, 202,
                                      211, 219, 226, 232, 237, 242, 245, 248, 256 };
static int ease(int t) /* t: 0..256 of the duration -> 0..256 */
{
    if (t <= 0) return 0;
    if (t >= 256) return 256;
    int i = t * 24 >> 8, f = (t * 24) & 255;           /* segment, fraction (Q8) */
    return BR_EASE[i] + ((BR_EASE[i + 1] - BR_EASE[i]) * f >> 8);
}
```
Durations: 80 / 161 / 321 ms are the tokens. CardPass's 100 / 130 / 120 ms sit between the feedback and element tiers; that may be a
deliberate "snappier on a tiny screen" choice. If so, keep it and just note it; if you want fidelity to the spec, use 161 ms for
slides/toasts and 80 ms for the selection cross-fade. Generate the table with a tool (like the other `tools/gen_br_*.py`) rather
than pasting it, so it follows the tokens.

## 4. A design question, not a bug: text size
The core derives type size from the visual angle (RESEARCH 6.1): a 300 mm handheld distance and this panel's 0.105 mm pixel pitch
give a **21 px** caption, which subtends 0.42 deg, the same angle as the web's 14 px caption at 500 mm. CardPass uses 12 / 13 px
Plex for list text, which subtends **0.24 / 0.26 deg, about 0.6 of that**. That is a legitimate density trade for a list that is scanned, set
in high-contrast ink, and read by the person who wrote it (you already disclose similar trades, e.g. Deep night). It is worth
knowing it is a trade rather than the evidence-based default, and worth testing on the device first; if 12-13 px is hard to read at
arm's length there, 21 px is the number the research supports. Nothing to change before the hardware arrives.

## Going the other way: what the core should take FROM CardPass
For the Bio-Resonant repo's own backlog, not for you to do here: CardPass's **contrast-preserving RGB565 quantisation** (every
ink keeps its exact Lc within 0.3; the core only checks Lc >= 60), the **strip renderer with DMA double-buffering and per-strip
hashes**, **4-bit anti-aliased fonts** (smaller than the core's 8-bit alpha bitmaps) and the **four circadian themes**.
